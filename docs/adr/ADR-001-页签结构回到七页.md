# ADR-001 · 页签结构回到 7 个（能力增长，页签不增长）

- 状态：已采纳（2026-11-05）
- 决策人：主管（用户）提问 + Lead 分析
- 影响面：`src/client.js` 的 `TABS`、全部页面文案

## 背景

v0.1.1 的原架构是 **7 个页签**：任务 / Bot / 房间 / 记忆 / 技能库 / 工作流库 / 设置。

v2 为对齐「记忆进化」的能力（`ANALYSIS-memory-evolve-parity.md`），补齐了
待办、便签、纪律、提示词四块能力，并**各开了一个页签**，页签变成 11 个：

```
任务 · 待办 · Bot · 房间 · 纪律 · 记忆 · 便签 · 提示词 · 技能库 · 工作流库 · 设置
```

主管质疑：**「待办和便签为什么单列 UI，是仿照记忆进化吗？和任务的关系是什么。」**
这个质疑命中了真问题。

## 分析：原架构的页签只有两种

| 类型 | 判据 | 例 |
|---|---|---|
| **协作对象** | 你有多个；每个有生命周期；需要点进去看详情；会被别的对象引用 | 任务、Bot、房间 |
| **配置资产** | 配置一次；被多处引用；不需要"逐个点进去操作" | 技能库、工作流库、设置 |

对照后发现，v2 新增的四个页签**两类都不属于**：

- **待办** = 任务的个人视图（同一件事的两种粒度，不是两种对象）
- **便签** = 一次性草稿（没有生命周期，甚至不算对象）
- **纪律** = AI 的规矩（记忆的同族：AI 该知道什么）
- **提示词** = AI 的指令模板（同上）

**根因**：把「能力对等」误当成「页面也对等」——memory-evolve 有独立页面，
这边就也各开一个。但页面结构应对齐**本平台的领域模型**，不是对齐别的插件的页面。

## 决策

**新增能力一律不新开页签**，只能作为既有页签内的子视图。页签数回到 **7**：

| 主页签 | 子视图 | 一句人话 |
|---|---|---|
| 任务 | 协作看板 / 我的待办 / 便签 | 要做的活 |
| Bot | — | 谁来做 |
| 房间 | — | 在哪商量 |
| 记忆 | 事实与偏好 / 纪律与要求 / 提示词 | AI 该知道什么 |
| 技能库 | — | 怎么做 |
| 工作流库 | — | 按什么步骤做 |
| 设置 | — | 平台怎么跑 |

## 对主管两个具体建议的回应

1. **「待办/便签融合到任务栏」→ 采纳**。理由：三者是**一条漏斗**——
   便签（想到就记）→ 待办（决定要做）→ 任务（决定交给谁做）。
   并且补了 **`POST /todos/promote`**（待办「派下去」按钮）把漏斗收口，
   否则只是换了个位置，没解决"两种东西并存"的困惑。

2. **「记忆/纪律/提示词融合到一个设置页」→ 采纳分组，但不放进设置**。
   理由：**记忆是高频操作的对象**（要增删改查、要归档、要按项目切），
   塞进设置页会让最常用的功能多点两层。改为在顶层**记忆**页下做三个子视图，
   分组逻辑正是主管说的那个分组（AI 该知道什么），只是不叫"设置"。

## 后果

- 页签数 7，与 v0.1.1 原架构一致；新增能力全部落子视图。
- 新增代码判据（写进 ARCHITECTURE.md §4）：
  > 新能力若没有独立生命周期、不需要多人/多 Bot 共同引用、不产生可点进去的详情，
  > 不许新开页签。
- 代价：子视图多一次点击才能到「便签」；用「一条漏斗」的心智抵消。
