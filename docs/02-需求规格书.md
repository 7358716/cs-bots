# cs-bots 改造07 需求规格书

> 版本：v0.7.0（改造07）
> 日期：2026-11-08
> 状态：已实现

---

## 1. 背景与目标

### 1.1 改造前的问题

cs-bots v0.6.x 有 10 个扁平页签，所有功能平铺在一起，人和 AI 的能力边界不分。用户提出三个核心诉求：

1. **分层**：把「人用的功能」和「AI 用的底层工具」分开
2. **穿透**：正常只看人用的，需要时能进底层查看/管理
3. **借鉴**：借鉴 DSH Super-agent 的三项能力（不借鉴 Source 外部事件驱动、不借鉴 Eval 准入模型）

### 1.2 改造目标

| 目标 | 验收标准 |
|---|---|
| G1 分层架构 | 6 个上层页签 + 7 个下层区块，职责清晰 |
| G2 穿透入口 | 顶部「⚙ 穿透」按钮，点开可见 7 个区块，每区块可展开详情 |
| G3 借鉴3 Subscription | 任务可订阅房间，房间消息自动作为上下文到达任务 |
| G4 借鉴4 阶段机 | 任务带 8 阶段派生信息，`needsPerson` 正确标识「该人动手」 |
| G5 借鉴5 prepare | Bot 可设准备命令，claim 前执行，失败不认领 |
| G6 文档交付 | 架构、需求规格、详设、操作手册四份文档 |
| G7 质量门禁 | 全部既有测试通过 + 新增测试覆盖新能力 |

### 1.3 明确不做的事

| 不做 | 原因 |
|---|---|
| 不借鉴 Source（外部事件驱动建任务） | 用户明确不要 |
| 不借鉴 Eval（准入模型/gate+assessment） | 用户明确不要 |
| 不引入第三方运行时依赖 | 保持零依赖纪律 |
| 不改动既有 38 个工具的契约 | 纯增量原则 |

## 2. 功能需求

### FR-1：分层导航

**描述**：把 10 个扁平页签重组为 6 个上层页签。

| 需求 | 说明 |
|---|---|
| FR-1.1 | 页签为：工作台、团队、记忆、技能库、数据、设置 |
| FR-1.2 | 工作台含：协作看板、复盘周期、我的待办、便签、成果 |
| FR-1.3 | 团队含：Bot 档案、团队、房间 |
| FR-1.4 | 记忆含：事实与偏好、纪律与要求、提示词 |
| FR-1.5 | 技能库含：技能、工作流 |
| FR-1.6 | 数据含：文件浏览、PDCA 测量 |
| FR-1.7 | 旧页签 id（tasks/bots/rooms/teams/artifacts）通过 `safeGoTab` 自动映射到新页签，向后兼容 |

**验收**：页面只剩 6 个页签；旧 `onGoto('tasks')` 等调用仍能正确跳转。

### FR-2：穿透面板

**描述**：顶部「⚙ 穿透」按钮打开右侧抽屉，显示 7 个下层区块。

| 需求 | 说明 |
|---|---|
| FR-2.1 | 区块为：注册表、唤醒桥、存储、路由、验证、建议、订阅 |
| FR-2.2 | 每区块显示 label + description + stats 概览 |
| FR-2.3 | 点击区块展开详情（GET `/deepdive/block/:id`） |
| FR-2.4 | 支持的区块操作：唤醒桥 flush、存储 replay |
| FR-2.5 | 未知区块返回 404 + 可读原因；不支持的操作返回 400 |
| FR-2.6 | 所有操作有明确返回值（成功/失败 + 人话） |

**验收**：`GET /deepdive/blocks` 返回 7 个区块；`POST /deepdive/op {block:'store',op:'replay'}` 成功。

### FR-3：Subscription 扇出（借鉴 Super-agent）

**描述**：任务可订阅房间，房间后续消息自动作为上下文到达任务。

| 需求 | 说明 |
|---|---|
| FR-3.1 | `subscribe(taskId, roomId, note?, by)` 创建订阅，幂等 |
| FR-3.2 | `unsubscribe(id, expectedRev?, by)` 取消订阅（终态） |
| FR-3.3 | `fanout(roomId, message, wake?)` 把消息扇出给订阅该房间的活任务 |
| FR-3.4 | 扇出**只加上下文，不改任务状态、不授予开工权力** |
| FR-3.5 | 上下文滚动窗口，默认保留最近 20 条（`fanoutKeep`） |
| FR-3.6 | 每条上下文文本截断到 2000 字符（防爆炸） |
| FR-3.7 | 扇出默认**不唤醒** owner（`wakeOnFanout:false`） |
| FR-3.8 | 房间发消息后（POST `/rooms/post`）自动触发扇出 |
| FR-3.9 | CAS：unsubscribe 带 `expectedRev` 不匹配即抛错 |

**验收**：订阅后发房间消息，任务 `context` 增加；取消订阅后不再增加。

### FR-4：工单阶段机（借鉴 Super-agent）

**描述**：任务带 8 个执行阶段的派生信息。

| 需求 | 说明 |
|---|---|
| FR-4.1 | 8 阶段：person/delivery、person/answer、person/review、person/blocked、person/failed、working/queued、idle、working |
| FR-4.2 | 判定自上而下首个命中（顺序即优先级） |
| FR-4.3 | 投递失败最高优先级 |
| FR-4.4 | 4 个 `person/*` 阶段 `needsPerson=true` |
| FR-4.5 | 纯函数，不落盘，不修改入参 |
| FR-4.6 | `GET /tasks` 每条任务带 `stageInfo`，响应带 `stageSummary` |
| FR-4.7 | `GET /tasks/detail` 和 `GET /tasks/summary` 带 `stageInfo` |
| FR-4.8 | 前端任务卡片显示阶段徽章，person 阶段用强调色 |

**验收**：新建任务显示「排队中」；完成未验收显示「等你验收」。

### FR-5：prepare command（借鉴 Super-agent）

**描述**：Bot 可设开工准备命令。

| 需求 | 说明 |
|---|---|
| FR-5.1 | Bot 注册表新增 `prepareCommand` 字段（可选） |
| FR-5.2 | 创建时带 `prepareCommand` 落盘 |
| FR-5.3 | `setPrepareCommand(id, prepareCommand, expectedRev, byId)` 设置/清除 |
| FR-5.4 | claim 前先执行 prepare；失败则不认领，任务保持原状 |
| FR-5.5 | 安全边界：命令首段必须在 `CMD_WHITELIST` 内 |
| FR-5.6 | 用 execFile 传参数组，不经 shell（无注入面） |
| FR-5.7 | 硬超时 10 分钟 |
| FR-5.8 | cwd 固定为 Bot 工作目录 |
| FR-5.9 | `prepare_command_set` 动作写入事件流（可审计） |

**验收**：设 prepare 后派活，prepare 成功则 claim 成功，失败则返回 `PREPARE_FAILED`。
